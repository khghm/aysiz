# فروشگاه تای سیز

فروشگاه پوشاک فارسی (React/Vite) با بک‌اند Node.js.

## اجرا

```bash
# پایگاه‌داده و بک‌اند
cd server
npm install
if (!(Test-Path .env)) { Copy-Item .env.example .env }
docker compose --env-file .env up -d postgres
# اگر فایل SQLite قدیمی دارید، این دو دستور را پیش از اولین راه‌اندازی اجرا کنید:
npm run migrate:sqlite
npm run migrate:sqlite -- --apply
node src/index.js                              # پورت 4000

# فرونت‌اند (ترمینال جداگانه، از ریشهٔ پروژه)
npm install
npm run dev                                    # پورت 3000
```

Vite پروکسی `/api` و `/mock-gateway` را به `http://127.0.0.1:4000` هدایت می‌کند؛ در صورت نیاز می‌توانید مقصد proxy را با `VITE_API_URL` تغییر دهید. ابتدا بک‌اند را اجرا کنید و سلامت آن را در `http://localhost:4000/api/health` بررسی کنید، سپس Vite را بالا بیاورید.
بک‌اند از PostgreSQL با `DATABASE_URL` استفاده می‌کند. واردسازی فقط به مقصد خالی انجام می‌شود، همهٔ جدول‌ها را در یک تراکنش منتقل می‌کند و فایل SQLite را تغییر نمی‌دهد. اگر مقصد داده داشته باشد، ابزار بدون نوشتن متوقف می‌شود؛ برای جزئیات و تنظیم مسیر منبع، [راهنمای بک‌اند](./server/README.md) را ببینید.

وضعیت رابط کاربری و داده‌های موقت سمت کاربر با Zustand مدیریت می‌شود. داده‌های دریافتی از API با TanStack Query cache می‌شوند: cache در حافظهٔ همان tab است، داده‌های عمومی معمولاً پس از ۶۰ ثانیه و داده‌های پنل پس از ۳۰ ثانیه stale می‌شوند و هنگام بازگشت focus قابل refresh هستند. تغییرات مجموعه‌های پنل optimistic نمایش داده می‌شوند و در صورت خطای ذخیره‌سازی rollback و دوباره از API بارگذاری می‌شوند. PostgreSQL همچنان منبع نهایی داده است؛ این cache بین مرورگرها/کاربران مشترک نیست و جایگزین cache سمت سرور یا CDN نیست.

برای deploy استاتیک frontend در Cloudflare، Worker/Pages به‌تنهایی بک‌اند Express یا PostgreSQL را اجرا نمی‌کند. بک‌اند باید جداگانه در دسترس HTTPS باشد و متغیر build `VITE_API_BASE_URL` را در تنظیمات Cloudflare روی origin آن (بدون `/api`) قرار دهید؛ سپس CORS بک‌اند را برای origin سایت مجاز کنید. اگر `/api/*` به بک‌اند متصل نباشد، سایت می‌تواند با دادهٔ seed فقط برای پیش‌نمایش بالا بیاید و عملیات ورود، سفارش و پرداخت کار نخواهد کرد. راهنمای کامل در [راهنمای تحویل پروداکشن](./PRODUCTION-HANDOFF.md) است.

برای راه‌اندازی production، secrets، استقرار HTTPS، اتصال زرین‌پال/کاوه‌نگار، انتقال دیتابیس به میزبان نهایی، کنترل‌های امنیتی و چک‌لیست تحویل، [راهنمای تحویل پروداکشن](./PRODUCTION-HANDOFF.md) را دنبال کنید. CORS allowlist، rate limit مبتنی بر PostgreSQL و security headers بک‌اند اکنون پیاده‌سازی شده‌اند؛ موارد باقی‌ماندهٔ امنیتی در راهنما مشخص‌اند و باید پیش از انتشار عمومی تعیین‌تکلیف شوند.

## مدیریت دسترسی ادمین و پشتیبان‌گیری

دسترسی پنل براساس نقش متصل به حساب مدیر در پایگاه‌داده اعمال می‌شود؛ تغییر انتخابی نقش در مرورگر مجوز ایجاد نمی‌کند. حساب‌های مدیر و نقش‌ها از بخش «سیستم و امنیت» مدیریت می‌شوند. ایجاد حساب مدیر به رمز حداقل ۱۲ کاراکتری نیاز دارد.

فایل پشتیبان بخش مدیریت، JSON کامل جداول PostgreSQL است و می‌تواند شامل اطلاعات شخصی مشتریان، hash رمزها و داده‌های OTP باشد. آن را محرمانه و رمزگذاری‌شده نگه دارید. بازیابی، داده‌های فعلی را در یک تراکنش جایگزین می‌کند؛ حساب مدیر جاری و نقش سیستمی آن حفظ می‌شوند و نسخه نامعتبر به‌طور کامل رد می‌شود. قالب پشتیبان دارای نسخه طرح‌واره است.

این قابلیت دستی، جایگزین پشتیبان‌گیری زمان‌بندی‌شده و خارج از سرور نیست. پیش از استفاده پروداکشن، ذخیره‌سازی امن خارج از میزبان، پایش موفقیت backup و آزمون دوره‌ای restore را راه‌اندازی کنید.

امتیاز وفاداری پس از تأیید پرداخت به حساب مشتری ثبت‌شده تعلق می‌گیرد و ثبت آن برای هر سفارش idempotent است. مبلغ مشمول، مبلغ کالا پس از تخفیف و پیش از مالیات و ارسال است. بازخرید در checkout تا سقف ۱۰٪ مبلغ کالا پس از کد تخفیف اعمال می‌شود؛ لغو سفارش پرداخت‌نشده، امتیاز رزروشده را بازمی‌گرداند.

انتساب افیلیت بر پایه آخرین کلیک معتبر تا پایان مهلت کوکی انجام می‌شود؛ پورسانت فقط پس از تأیید پرداخت ثبت می‌شود و callback تکراری پورسانت را تکرار نمی‌کند. نرخ هر دسته در صورت تعریف بر نرخ پلکانی پایه اولویت دارد و پاداش سطح به آن افزوده می‌شود؛ تخفیف سفارش و امتیاز وفاداری متناسب با اقلام از مبلغ مشمول کسر می‌شوند. تسویه فقط پورسانت ثبت‌شده را رزرو می‌کند؛ ثبت «پرداخت‌شده» به معنی ثبت دستی حواله‌ای است که بیرون از سامانه انجام شده، نه انتقال بانکی از پنل.

وضعیت مرسوله، حامل، کد رهگیری و رویدادهای دستی در رکورد سفارش ذخیره و همراه backup منتقل می‌شوند. استعلام و چاپ برچسب شرکت حمل متصل نیست؛ وضعیت‌های ارسال و تحویل فقط از گردش مرسوله به‌روزرسانی می‌شوند.

طبق سیاست فعلی، کمپین‌های خودکار checkout و همهٔ اتوماسیون‌های پیام خاموش هستند؛ فقط کدهای تخفیف اعتبارسنجی‌شده اعمال می‌شوند. هیچ پیام بازاریابی بدون provider فعال و رضایت ثبت‌شدهٔ مشتری ارسال نمی‌شود.

مشتری واردشده می‌تواند برای کالای سفارش پرداخت‌شده و تحویل‌شدهٔ متعلق به حساب خود درخواست مرجوعی ثبت کند؛ تعداد درخواستی با مجموع درخواست‌های فعال کنترل می‌شود. در گردش مرجوعی، ثبت بازپرداخت فقط با مبلغ صحیح و مرجع حواله‌ای که واقعاً خارج از سامانه انجام شده ممکن است؛ مبلغ بازپرداخت‌شده در دفتر مالی ثبت و از درآمد خالص گزارش‌ها کسر می‌شود. سامانه انتقال وجه انجام نمی‌دهد و موجودی کالا را تغییر نمی‌دهد؛ بررسی و اصلاح موجودی بر عهده انباردار است. پورسانت تسویه‌نشده سفارش دارای بازپرداخت تا بررسی دستی از تسویه خارج می‌شود. مدیر می‌تواند پس از بررسی، پورسانت را آزاد یا استحقاق آن را رد کند؛ تصمیم در audit ثبت می‌شود و پورسانت‌هایی که پیش‌تر پرداخت شده‌اند خودکار پس گرفته نمی‌شوند.
